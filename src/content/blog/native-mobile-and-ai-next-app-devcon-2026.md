The Berlin version of my native mobile and AI talk, this time shared with Filip Dolník. The first half is mine: mobile is a special case because two apps do the same thing, so the first platform is the spec for the second. Shopify's move from React Native back to native gets a section of its own. In the second half, Filip explains why analyzing two entire apps reliably is not something you can just ask a coding agent to do, and how our analysis engine uses code to orchestrate agents instead.

## Practical tips

- **[12:29 — General AI tips](https://www.youtube.com/watch?v=twf41nSUqPA&t=749s)** — A real how-to would be a whole class. These are the critical things if you're running into problems.
- **[12:46 — Context is critical](https://www.youtube.com/watch?v=twf41nSUqPA&t=766s)** — Wasted tokens, explaining things over and over, dumb work: that's almost always your context. A single agent file is probably not enough.
- **[13:04 — The consultant you have for an hour](https://www.youtube.com/watch?v=twf41nSUqPA&t=784s)** — Every team has an incomplete, stale wiki and someone who tells you not to use the architecture library a dev left behind three years ago. Whatever you don't tell the model, it guesses at, and that's where the weird stuff comes from. It reads well, so tell it once.
- **[13:46 — Don't trust context management plugins](https://www.youtube.com/watch?v=twf41nSUqPA&t=826s)** — If it were easy to manage automatically, it already would be. On the plane I told an agent not to run tests; it saved that to memory, and back at the hotel it still wouldn't run them.
- **[14:09 — Agent fundamentals](https://www.youtube.com/watch?v=twf41nSUqPA&t=849s)** — Every message and tool call lives in the context window. Most models have a million tokens; don't get anywhere near it, or you get rot. Compacting is a short summary that doesn't remember what you think it does. Use phased plans and subagents.
- **[14:31 — It's a new skill](https://www.youtube.com/watch?v=twf41nSUqPA&t=871s)** — It's simple for a prototype and much less so after that. "If I have to, I'll learn it in a week." You will not.
- **[14:54 — The workflow](https://www.youtube.com/watch?v=twf41nSUqPA&t=894s)** — Triage, design, adversarial review, implementation and tests, review, commit, with each step able to kick work back. That's becoming standard.
- **[15:23 — PR review will change too](https://www.youtube.com/watch?v=twf41nSUqPA&t=923s)** — The complaint that AI leaves humans reviewing everything is valid for now. But with UI validation and automated testing, you won't need to look at every button radius change, just the parts that matter, like your transaction handling.

## Shopify goes native

- **[16:19 — Shopify](https://www.youtube.com/watch?v=twf41nSUqPA&t=979s)** — I've focused on AI for cross-platform native since early last year and seen almost nobody else talk about it. Then this dropped: native is now the future of mobile at Shopify, from Mustafa, their head of mobile. As a KMP person, I remember their 2020 React Native announcement as an oddly sad day.
- **[17:25 — What the post says](https://www.youtube.com/watch?v=twf41nSUqPA&t=1045s)** — Implement features on one platform using the other as a reference, which sounds a lot like the first platform is the spec. Help developers contribute outside their primary platform. Dramatically reduce the cost of maintaining parity.
- **[18:00 — Parity with AI](https://www.youtube.com/watch?v=twf41nSUqPA&t=1080s)** — Shopify talks about process to maintain parity. Our tool, Parive, uses AI to analyze, monitor and plan fixes so the two apps actually do the same thing. If you use AI for everything else, using it to check that is a no-brainer.
- **[18:40 — Helix](https://www.youtube.com/watch?v=twf41nSUqPA&t=1120s)** — The tempting approach is to point Claude Code at the codebase, have it write spec docs, and implement everything. Shopify's tool breaks the work into small checkpoints, verifies each one, and feeds the feedback back in so the loop improves.
- **[19:13 — How Helix works](https://www.youtube.com/watch?v=twf41nSUqPA&t=1153s)** — A screen, roughly a feature, is broken into tasks. Each is built and tested, the screens are shown side by side, AI runs adversarial review, and a human approves at the end. Any stage can kick work back.
- **[19:39 — What's standard, and what's new](https://www.youtube.com/watch?v=twf41nSUqPA&t=1179s)** — Breaking down work, design, test and review have become standard practice. The mobile-specific tasks (structure first, then UI) and the side-by-side visual review are new. We've been experimenting with multimodal comparison, but having a developer check visually is practical.
- **[20:33 — Testing from underneath](https://www.youtube.com/watch?v=twf41nSUqPA&t=1233s)** — UI testing became the bottleneck for agents, so Shopify built their app so a CLI drives the UI directly, without simulated clicks. I can't tell you to rearchitect your app, but I expect this to become common.
- **[21:29 — The payoff](https://www.youtube.com/watch?v=twf41nSUqPA&t=1289s)** — Twelve weeks, six devs. Cold start times way down, ten times fewer crashes, a smaller Android release, and great build times. Go read the post.

## What we're building

- **[21:56 — The port tool](https://www.youtube.com/watch?v=twf41nSUqPA&t=1316s)** — Our first, unnamed tool ports large production apps, and it is surprisingly effective and efficient. But then you have two apps, and the big problem is keeping them in parity going forward.
- **[22:35 — Parive](https://www.youtube.com/watch?v=twf41nSUqPA&t=1355s)** — It analyzes and normalizes screens, features, terminology and user stories, and compares them between the apps.
- **[22:46 — Analysis has to be repeatable](https://www.youtube.com/watch?v=twf41nSUqPA&t=1366s)** — You need apples-to-apples comparisons to find the edge cases and error states that differ even when the screens look the same. The analysis updates as commits land.
- **[23:21 — History, notes and plans](https://www.youtube.com/watch?v=twf41nSUqPA&t=1401s)** — Trace history to find out why something differs and whether it's intentional, with notes and eventually issues and Slack. Then generate a plan to close the gap and run it in Claude Code or in our agent, which opens a PR.
- **[23:50 — Public preview](https://www.youtube.com/watch?v=twf41nSUqPA&t=1430s)** — A full analysis of the Wikipedia iOS and Android apps, from June, with a new engine landing soon. Accurate analysis is critical, which is Filip's part.

## Filip: Building the analysis engine

- **[24:18 — Why a specialized tool?](https://www.youtube.com/watch?v=twf41nSUqPA&t=1458s)** — The analysis has to cover the entire project at once, and scale is the primary problem; most of this doesn't apply to projects under about 10,000 lines. The output also has to be a source of truth you can build on.
- **[25:06 — Cost, time and quality](https://www.youtube.com/watch?v=twf41nSUqPA&t=1506s)** — LLMs aren't cheap, so the cost has to make sense against the value. Projects change fast; if the analysis takes days, it will always be stale. And the output has to be trustworthy.
- **[25:49 — Soundness and completeness](https://www.youtube.com/watch?v=twf41nSUqPA&t=1549s)** — Terms from static analysis. Sound: everything it reports about an item, like a screen, is correct. Complete: it finds every such item. Both, every run.
- **[26:33 — Why not just ask Claude?](https://www.youtube.com/watch?v=twf41nSUqPA&t=1593s)** — Coding agents aren't designed for this. AI makes mistakes, more of them as tasks get harder, so mistakes grow quickly with project size.
- **[27:07 — Agents are lazy](https://www.youtube.com/watch?v=twf41nSUqPA&t=1627s)** — On open-ended tasks they don't know when they're done; nobody knows up front how many screens there are. Push harder and you get the inverse: ask an agent to fix a hundred bugs, and it will, even if it has to disagree with you about what a bug is.
- **[28:23 — Variance between runs](https://www.youtube.com/watch?v=twf41nSUqPA&t=1703s)** — Run the same thing twice and you get very different results, assuming you've isolated the agents so they can't copy each other's answers. Switch models or providers for funnier results. "What are all the screens" should always have the same answer.
- **[29:24 — Bring back code](https://www.youtube.com/watch?v=twf41nSUqPA&t=1764s)** — The fundamental problem is using LLMs for what they aren't good at. Code orchestrates the agents instead: a dedicated session per file, so every run is guaranteed to look at every file.
- **[30:32 — Many small problems](https://www.youtube.com/watch?v=twf41nSUqPA&t=1832s)** — Splitting the work means sessions run in parallel; the engine can run thousands at once, so hours with a coding agent become minutes. Simpler tasks leave less room for mistakes.
- **[31:18 — A model 100 times cheaper](https://www.youtube.com/watch?v=twf41nSUqPA&t=1878s)** — Coding agents often need something like GPT-Sol or Astra. Simple tasks get away with something like Luna, which is 100 times cheaper than Astra, without using noticeably more tokens. That saving carries straight through to the cost of the analysis.
- **[31:58 — Code for everything else](https://www.youtube.com/watch?v=twf41nSUqPA&t=1918s)** — The LLM should be the last resort. Structured data instead of text, and custom tools so each agent can only do the operations its task needs.
- **[32:53 — Exit gates](https://www.youtube.com/watch?v=twf41nSUqPA&t=1973s)** — Be mean to your agents: they can't call a task done until code checks the output. If an agent makes a claim about a file its tool calls show it never read, send it back to read it.
- **[33:43 — A second agent judges](https://www.youtube.com/watch?v=twf41nSUqPA&t=2023s)** — Where code can't check the result, a separate session reviews the output or the log and sends feedback to the original. Agents, like people, are better at judging an answer than producing it.
- **[34:30 — Split the review too](https://www.youtube.com/watch?v=twf41nSUqPA&t=2070s)** — Dedicated agents look for mistakes in individual items, others for missing items, others for duplicates.
